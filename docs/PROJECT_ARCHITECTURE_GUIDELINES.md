# Rafael Brothers — Modular Architecture & Project Organization

## מטרת המסמך

הנחיית עבודה קבועה לפיתוח **האחים רפאל (Rafael Brothers)** — משחק פלטפורמה דו־ממדי לדפדפן המבוסס על Phaser / HTML5, עם סרט מדידה המשמש כחבל עגינה ונדנוד, שתי דמויות, שלבים, אויבים ואתגרים סביבתיים.

**המטרה:** להפוך את הפרויקט לתשתית משחק יציבה ומודולרית, שבה אפשר להוסיף שלבים, רקעים, אנימציות, אויבים ואתגרים דרך נתונים ורכיבים חוזרים, בלי להעתיק או לשכתב את מכניקות המשחק.

**אין להתחיל מחדש, אין להחליף מנגנונים שעובדים, ואין למחוק יכולות קיימות.** הגרסה האחרונה שנבדקה בפועל היא מקור האמת להתנהגות המשחק; קובצי מקור ישנים אינם מחליפים אותה אוטומטית. יש לאמת את הגרסה והקבצים הזמינים בכל תחילת משימה.

## 1. Architecture Audit לפני פיתוח

קרא את קוד המקור, קובצי הפרויקט, סכמות ה־JSON, היסטוריית המיילסטונים, דוחות ה־QA ו־`HANDOFF.md`. מפה את מערכות המשחק, תלויותיהן, ערכים קשיחים בקוד, כפילויות ומקורות אמת מתחרים. הבחן בין מערכת שעובדת אך תלויה בשלב הראשון לבין מערכת כללית באמת. שמור עותק בסיס בלתי משתנה לצורכי השוואה ונסיגה.

## 2. הפרדה ברורה בין שכבות

**Game Core — קבוע בכל המשחק:** פיזיקת Phaser, תנועת רפי ושאול, קפיצה, החלפת דמויות, סרט המדידה ומצבי הנדנוד Manual / Classic / Hybrid, ניהול התנגשות, מצלמה, HUD, סאונד, אנימציות, שמירה/Respawn, סיום שלב וטלמטריה. אין לשנות את הפיזיקה והתחושה של הסרט במסגרת ארגון קוד.

**Reusable Prefabs — מימוש חוזר:** עץ יציב או רקוב, עץ מתפורר, גשר שורשים, פטרייה מקפיצה, רשת דביקה, עכביש, שק ביצים, עכבישונים, נקודות עגינה, כלים, אויבים, מחסומים וטריגרים. לכל סוג רכיב מימוש אחד עם מחזור חיים `create → update → disable → reset → destroy`.

**Stage Data — תוכן משתנה:** מידות עולם, קרקע, תהומות, מיקום אובייקטים ואויבים, נקודות עגינה, תנאי הפעלה, רקעים, שכבות Parallax, אווירה, נכסים, אנימציות, Checkpoints ונקודת סיום. נתונים אלה יוגדרו בקובצי JSON בעלי סכמה וגרסה ברורות, לא כמיקומים מפוזרים בקוד.

**Tools & QA — כלים עצמאיים:** Stage Loader, רישום Prefabs, בדיקות סכמת JSON, תצוגת שלב, בדיקות עבירות, טלמטריה ובדיקות דפדפן.

## 3. כלל מקור האמת

מיקום, גודל או פרמטר של אובייקט צריכים להיות מוגדרים במקום אחד בלבד. לדוגמה: הזזת עץ מתפורר ב־JSON צריכה להזיז יחד את האיור, משטח ההתנגשות, נקודת העגינה, אזור הטריגר ומקום הנפילה. אין לשכפל אותם בקוד. השתמש במזהים יציבים והפניות לנכסים; הימנע מפיצול מוגזם לקבצים זעירים.

## 4. Stage Schema & Loader

תכנן סכמת `stage.json` בעלת גרסאות, עם ולידציה, גבולות עולם, אובייקטים, נקודות עגינה, רקעים, מערכות אווירה, נקודות התחלה/סיום ומאפייני אתגרים. בנה Stage Loader ו־Prefab Registry באופן מדורג. הוכח שאפשר לשנות לפחות שלושה רכיבים קיימים מתוך נתוני השלב בלי לערוך את המנוע. שמור על אפשרות לייצא **HTML עצמאי אחד** להפעלה בדפדפן.

## 5. עולם חזותי ואנימציות

הפרד בין רקעים דקורטיביים, אובייקטים במישור המשחק ואובייקטים אינטראקטיביים. שכבות Parallax יגיבו לתנועת **המצלמה**, ולא באופן שרירותי לנדנוד השחקן. קורים שנמתחים מענף יוכלו להגיב בעדינות למתח בעוגן הספציפי שאליו הם מחוברים; קורי רקע מרוחקים לא צריכים להתנדנד יחד עם השחקן. הכין ספריות נכסים, ספרייטים, אנימציות ואודיו לשימוש חוזר בכל שלב, בלי לייצר תוכן חדש רק לצורך שינוי הארכיטקטורה.

## 6. Platformer Challenge Forge

בדוק את הגרסה המותקנת בפועל של **Platformer Challenge Forge** ואת יכולותיה לפני שמסתמכים עליה. שמור אותו ככלי **עצמאי ואוניברסלי לתכנון אתגרים, הצעות מפה, בדיקות גאומטריה וסימולציות עבירות** — לא כמנוע הפיזיקה של המשחק. תכנן מתאם בינו לבין סכמת השלבים והפרופילים העדכניים של רפי ושאול. בדיקות Forge אינן תחליף לבדיקה במשחק האמיתי בדפדפן. אל תשדרג פלאגין מותקן בלי משימה והרשאות מתאימות.

## 7. אופן העבודה

עבוד במקטעים קטנים במחזור **Development → QA → Fix**. לפני כל שינוי: אמת Baseline, בנה מבחן רגרסיה ותעד סיכונים. אחרי כל שינוי: הרץ בדיקות קוד, Build, בדיקות דפדפן ובדיקות אינטראקציה. בדוק במיוחד סרט מדידה, חציית תהום, החלפת דמויות, קורים דביקים, עכבישונים, עצים קורסים, גשרים, נקודות עגינה, מודולים ניתנים לכיבוי, רקעים, Restart וסיום שלב. כיבוי רכיב חייב לנקות גם התנגשות, טריגרים, מאזינים ועוגנים — לא רק להסתיר ציור.

## 8. סדר פיתוח מועדף

1. **Audit + Architecture + JSON Schema** — מפה את המערכת והגדר מקור אמת.
2. **Stage Loader + Prefab Registry POC** — העבר מספר רכיבים קיימים בזהירות.
3. **Migration מדורג של שלב 1** — בלי שינויי משחקיות בלתי מתוכננים.
4. **בדיקת תאימות Forge ומתאם** — אחרי שהסכמה יציבה.
5. **ספריית אנימציות ונכסים** — ורק אז הרחבת שלבים, אויבים ואתגרים.

## תוצרים מחייבים בכל מיילסטון

- קוד מקור מלא וקובצי הגדרות.
- HTML שחיק, כאשר השתנה המשחק הרץ.
- ZIP לשחזור העבודה.
- `CHANGELOG.md`, `HANDOFF.md`, `QA_REPORT.md`, `KNOWN_ISSUES.md`.
- פירוט מה הושלם, מה נבדק בפועל ומה נדחה, ללא הצגת סימולציות או בדיקות חלקיות כהוכחת משחקיות מלאה.

**עקרון מנחה:** מנוע המשחק אחראי ל־**איך** דברים מתנהגים; נתוני השלב אחראים ל־**מה נמצא בעולם והיכן**; Forge מסייע לתכנן ולבדוק **האם האתגרים הגיוניים ועבירים**. המשך פיתוח רק כשהגבולות האלה ברורים ונבדקו.
