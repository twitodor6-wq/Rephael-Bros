**נקודת המוצא המחייבת: `Rafael_Brothers_M470_Source_QA.zip` — M4.7.0, Managed Encounters & Isolated World Fixture.** החבילה מצורפת בנפרד לשיחת העבודה. אין להתחיל מחדש ואין לחזור לגרסאות מוקדמות. אם קיימת גרסה חדשה יותר, יש לזהות ולאמת אותה לפני השינויים ולא לדרוס עבודה מאוחרת.

## 2. יעד A — הרחבה מורגשת של יער השורשים בשלב 01

הרחב את מסלול המשחק של Stage 01 כך שהשחקן יבחין באזור יער שורשים נוסף בעל תכלית משחקית, ולא רק במסך רחב יותר או שכפול דקורציה.

- תכנן קודם **מפת Before/After** עם אזורי משחק, נקודות מעבר, בורות, נקודות עגינה ואתגרים קיימים. תעד את סדר המפגשים ואת תפקידו של כל אזור.
- בחר את אופן ההרחבה הבטוח ביותר לפי הקוד בפועל: הארכת גבולות העולם, העברת נקודת הסיום לקצה החדש, המשך של גשר/שביל שורשים, או שימוש חוזר באובייקטים קיימים. אל תוסיף עולם שני או סצנת Game חדשה.
- ודא שהמצלמה, גבולות העולם, מעקב השחקן, Parallax, רקע/אווירה והמעבר אל השער החדש נשארים תואמים. אל תחליף רינדור מאושר או תגרום לגלילת רקע שמושפעת שגוי מתנודות החבל.
- העדף תוספות Data-driven עם מזהים יציבים; עבור גאומטריה שהקוד עדיין מגדיר באופן קשיח, בצע מיגרציה נקודתית בלבד עם מבחן לפני ואחרי. **אל תפעיל ב־Stage 01 את `world.terrain` של ה־fixture על גבי הגאומטריה הישנה אם התוצאה היא התנגשות כפולה או שני מקורות אמת.** אם מיגרציה זו עדיין מסוכנת, השתמש במסלול הייצור הקיים ותעד את הגבול.
- שמור תצורת `s01` ישנה/מצב rollback נפרד שאפשר לבנות ממנו מחדש, בלי לייצר שני מקורות אמת פעילים לאותו build.

**הוכחת הצלחה:** Build חדש מציג ב־Chromium אזור משחק מורחב בפועל, המצלמה עוקבת ומוגבלת כראוי, השחקן יכול להתקדם אליו ולחזור או להגיע ליציאה, ולא נוצרו משטחי התנגשות בלתי נראים/כפולים.

## 3. יעד B — העץ המתפורר מעל התהום, מתוך JSON בלבד

נצל את רכיב `falling-bridge-tree` הקיים ואת ה־Managed Actor שלו; **אין לממש מנגנון נפילה חדש**.

1. תכנן מיקום מאתגר אך הוגן מעל חלק מתאים של הבור/המסלול המורחב. אל תבחר קואורדינטות אקראיות: בדוק טווחי תנועה, מצלמה, גובה, הגעה לאחיזה והיכולת לצאת מהסיטואציה.
2. השתמש במיקום `position` של `falling-bridge-tree` וב־offsets/מידות שקיימים ב־JSON (`stubOffset`, `bridgeOffset`, `stubSize`, `bridgeSize`, `anchor`) כדי להעביר את **העץ, הציור, גוף ההתנגשות, משטחי הענף, נקודת העגינה, אזור ההתרעה והחלק הנופל יחד**. בצע הוכחת JSON mutation בפועל; אל תקבע מחדש את המיקום בקוד.
3. שמור על אותו מזהה עוגן ועל סדר בחירת העוגנים ב־Registry, כדי שלא תשתנה בחירת מטרת החבל. אל תיצור Registry חלופי ואל תחליף אותו במהלך ריצה.
4. בדוק את זמן ההתרעה וההתמוטטות הקיים, הנחיתה/הנפילה לאחר הקריסה, היכולת להתחבר ולהתנתק מהעץ, ומצבי Manual/Classic/Hybrid. **אין לשנות את זמני המכניקה או פיזיקת הסרט ללא ראיה ברורה ודו"ח נפרד**; התאם קודם גאומטריה וסדר אתגרים.
5. בדוק כיבוי דרך Stage Modules: אין Collider/גוף/טריגר/עוגן פעיל לאחר כיבוי; Reset/Restart משחזרים את המצב; כשל בבנייה אינו משאיר משאבים חלקיים.
6. בדוק שעץ שהתמוטט אינו נועל את ההתקדמות לצמיתות, אלא אם מדובר בהחלטת עיצוב מפורשת עם דרך התאוששות מאומתת.

**הוכחת הצלחה:** שינוי יחיד ב־JSON מזיז את הגאומטריה הנראית ואת ההתנהגות הפיזיקלית לאותו אזור, והאתגר אכן פעיל ונגיש בדפדפן האמיתי, כולל מצב קריסה והתאוששות.

## 4. יעד C — רצף אתגרים שניתן לערוך ב־JSON

בנה רצף קטן ומגובש מתוך **האובייקטים והמכניקות שכבר קיימים**. דוגמה רעיונית, לא סדר כופה: היכרות עם שורש/עוגן בטוח → חציית אזור מסוכן → עץ מתפורר מעל תהום → נחיתה באזור שורשים נוסף → מפגש עם האתגרים הקיימים → שער הסיום.

- תאר את הרצף באמצעות מזהים יציבים, מיקומי Prefabs, תלויות ו־Stage Modules; העדף שימוש במבנה Stage v1 ובצרכנים שכבר קיימים.
- **אל תוסיף שדה JSON רק משום שאפשר להגדירו.** אם דרוש שדה חדש כגון `challengeSequence`, הוסף אותו רק יחד עם: סכמה, בדיקת ולידציה, צרכן Runtime ממשי, הוכחת mutation ו־rollback. שדה תכנוני בלבד אינו יכול להיחשב כיכולת פעילה.
- ודא שאפשר לערוך לפחות **שני מאפיינים בעלי משמעות משחקית דרך JSON** (למשל סדר מרחבי של מפגשים ומיקום עוגן/גשר) בלי לערוך JavaScript; הדגם שתי וריאציות בטוחות של המסלול.
- רמות קושי ייקבעו דרך מרחקי קפיצה/נדנוד, ריווח פלטפורמות, מיקום עוגנים ותזמון הקיים של המכשולים — לא דרך שינוי נוסחאות החבל.
- תעד מפת שלב/SVG פשוטה או צילום אבחוני של המפה, בתוספת קשרים בין האתגרים; תוצר תצוגה אינו מקור אמת שני.
- ודא שקיימת דרך אמיתית לסיים את השלב לכל הפחות בדמות/מצב השליטה הראשיים, וש־Restart מחזיר את כל רצף האתגרים למצב הצפוי.

## 5. Development → Critical QA → Fix → Retest

בצע מחזורי פיתוח ממוקדים: הרחבת העולם → QA ותיקונים; העברת העץ → QA ותיקונים; חיבור הרצף → QA ותיקונים. אל תדחה את כל האימות לסוף.

### בדיקות חובה

**Baseline / Build / Source**
- שמור hash של חבילת M470, ה־HTML המקורי, הגדרת `s01.stage.json` ומודולי פיזיקה מאושרים. אל תדרוס את המקור הבלתי משתנה.
- הרץ `npm run build`, `npm test`, ולידציית JSON וסכמות עם הבדיקות הקיימות; הוסף בדיקות ממוקדות ל־M471.
- ודא שקובץ ה־HTML העצמאי נבנה עם התוכן החדש ושה־ZIP משחזר את אותו build.

**בדיקות דפדפן ומשחקיות אמיתית**
- הגעה לאזור יער השורשים החדש, מצלמה/Parallax, נראות רצף האתגרים ושער הסיום.
- רפי ושאול, תנועה, קפיצה והחלפת דמויות.
- חציית הבור בשלושת מצבי Manual / Classic / Hybrid, לרבות תרחישים עם התארכות/קיצור וניתוק החבל; ההבדל בין נפילה תקינה לתקלה הוא קריטי.
- העץ המתפורר: עמידה, משיכה, התרעה, התמוטטות, מגע, תוצאה; הוכחת התאמה בין ציור, Anchor ו־Collider.
- העכביש הגדול, רשת דביקה, שק עכבישונים, גשרים, עץ רקוב, עוגנים יציבים ושבירים, Stage Modules, Restart/Respawn, שער סיום ו־F3/ייצוא JSON.
- שינוי JSON בגרסת בדיקה בלבד: הזזת העץ, העברת יעד היציאה/מצלמה במידת הצורך והחלפת סדר אתגרים; בדוק את Phaser Graphics, bodies, overlaps ו־registry refs בפועל — לא רק את תוצאת הפונקציה הטהורה.

**Lifecycle / משאבים / ביצועים**
- בדוק לפחות **15 מחזורי Restart/Disable/Enable** לאתגרים שהועברו ואת ספירות Graphics, Bodies, Colliders, Timers, Listeners ו־Anchors לאחר frame settlement. אין גידול עקבי או כפילות עוגנים/מאזינים.
- בדוק כיבוי של רכיב בזמן שהאתגר פעיל וכשל בנייה חלקי אם שינית את ההקצאות.
- בדוק זמן frame, `dt`, קלט, חיבור/גלגול/שחרור בזמן חציית הבור; השווה את אותו תרחיש ל־M470 כאשר ניתן. דיווח על שינויים בתחושת משחק דורש עדות ממשחק אמיתי, לא סימולציה בלבד.
- **כשל Hybrid ברינדור רגיל:** השאר בנפרד את FAIL ההיסטורי של M468/M469. הרץ בדיקות בחומרה/renderer הנתונים, עם ובלי בידוד ציור, ופרט PASSED, FAILED או NOT TESTED בכל תרחיש. אין למחוק כשל היסטורי משום שבדיקה חדשה עברה.
- נסה פתיחה ישירה של HTML מתוך `file://` אם המדיניות מאפשרת; אם חסום, סמן **NOT TESTED** וספק הוראות בדיקה ידנית. Safari ותחושת משחק אנושית מסומנים NOT TESTED אם לא נבדקו בפועל.

**קריטריון מסירה:** לא נותרו רגרסיות חדשות בלתי מתועדות. כשל חדש ב־Core או בסרט המדידה הוא Blocker; יש לתקן או להחזיר לאחור את השינוי האחרון, לא להסוות בדוח.
