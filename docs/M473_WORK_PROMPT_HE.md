## מטרה משחקית

השחקן צריך לחוות **מסלול נינג'ה דו־ממדי**: לומד מכניקה בסביבה סלחנית, מתרגל אותה, נתקל בגרסה לחוצה יותר, ולבסוף משלב קפיצה, תנועה, סרט מדידה ועוגנים. בונה השלבים העתידי ירכיב **Challenges**, לא רק יפזר Prefabs. **במיילסטון הזה בנה והוכח רצף ידני, מודולרי ושחיק**; מחולל אוטומטי מלא הוא M4.7.4 ולא חלק מהמסירה הזו.

## ממצאים מהמשחק והקוד — לתיקון

1. `ceiling-spider`: קיים במשחק המקורי, אבל בלוח Stage Modules מוצג `Ceiling spider · always enabled in this release` במקום מודול שמאפשר ON/OFF בפועל.
2. `rotten-root-ledge`: מופע יחיד, אזהרת דריכה 650ms ועוד אזהרת קריסה 1800ms; התוצאה כרגע נחיתה על משטח בטוח. זה מוכיח מצב מכני אך בקושי מחייב תגובה. הכן לו תפקיד משחקי ברור, תוך שמירה על מופע ההדרכה הישן או התאימות שלו.
3. `fallen-bridge-tree`: העץ הנופל מייצר *גשר חלקי* בתוך הבור הראשון; הוא אינו שקול לגשר שמתפורר תחת השחקן. **שמר את התנהגות ה־bridge-fragment הקיימת**, ופתח Prefab/variant אחר לנפילת משטח בזמן מעבר, אם זו הדרך הבטוחה ביותר. אל תשנה את המכניקה הישנה כדי להתחזות למכשול אחר.
4. `Stage 01`: הבור הראשון x370–706 והבור השני x1190–1270. עוגן הבור השני המתוקן הוא x1230,y260. אין להחזיר את תקלת 'Tape blocked by roots'.
5. לפי שתי הקלטות המשתמש (אם צורפו), קיימת תנועת שחקן אמיתית לאורך השלב, אך פורמט הטלמטריה `M4.1.3` מתאר את גרסת **sampler**; אל תפרש זאת כגרסת מוצר M4.1.3 או כהוכחה מפורשת לאירוע קריסה. נדרשת טלמטריית Prefab חדשה או בדיקת runtime מפורשת.

## משימה A — מערכת מופעים חוזרים של מכשולים

אפשר מספר מופעים של לפחות סוג אחד של מכשול מתפורר במקביל, עם `id` ייחודי לכל מופע, config, state, timer, collision, anchorRefs אם נדרשים, reset/destroy ו־diagnostics מופרדים. שמור על lifecycle `create/update/disable/reset/destroy` או החוזה העדכני הקיים; אל תיצור timers, colliders, input listeners או Graphics דולפים.

תמוך ב־Stage JSON בנתונים מפורשים ותקפים עבור מופעים חוזרים, לרבות זמני התרעה/קריסה, trigger, footprint וסוג תוצאה. הבחנה בין `falling-tree-bridge` (עץ שנופל ויוצר גשר) לבין `collapsing-platform`/גזע שנשבר **מתחת לשחקן** חייבת להיות בנתונים ובקוד, לא רק בתווית UI. אין צורך במיגרציית Stage v2 רחבה; בצע הרחבה additive ל־Stage v1 רק אם היא נדרשת ועומדת בחוזי backward compatibility.

## משימה B — שני אתגרים שחיקים ומדורגים ב־Stage 01

בנה לפחות **שני מקטעי אתגר חדשים או שדרוגים שחיקים** במסגרת Stage 01, עם רצף לימוד → התנסות → סיכון עולה. השתמש ב־JSON כתוכן היחיד; אל תצייר מסלול שאין לו גופי התנגשות אמיתיים.

**Challenge 1 — גזע לגזע (למידה):** כמה פלטפורמות/גזעים בגבהים ובמרווחים שונים; הראשונה יציבה, ולאחר מכן גזע מתפורר בעל אזהרה קריאה ומרווח תגובה נדיב; נפילה ראשונה סלחנית או בעלת נתיב התאוששות. השחקן נדרש לבצע קפיצה מתוזמנת אחת לפחות.

**Challenge 2 — גשר מתפורר / חילוץ בסרט (שילוב):** מקטע ארוך יותר או רצף פלטפורמות שמתחיל להתפורר עם דריכת השחקן. חלון תגובה מהיר יותר מהאתגר הראשון, אבל עדיין קריא והוגן. יש להציג פתרון מכוון וברור — ריצה וקפיצה, או התחברות לעוגן יציב והיחלצות. תכנון החלופה בסרט חייב לעבור את Rope Crossing Safety Validator ותיקוף live, כולל מצבי Manual/Classic/Hybrid ורפי/שאול. אם משתמשים בעוגן שביר, הסבירו האם זה חלק מאתגר נפרד וכיצד נמנע מצב בלתי אפשרי.

**לא לבצע:** להזיז את עוגן x1230 או לשנות את פיזיקת הסרט כדי 'לפתור' קושי; להוסיף שלב 02; להכניס אויבים/נכסים חדשים חסרי אישור; לכפות מוות בלי אזהרה; להעביר את המשחק כולו למנוע פיזיקה אחר.

מותר להרחיב את האזור המזרחי של Stage 01 ולהעביר את שער הסיום **רק דרך Stage JSON**, אם נדרש מקום לרצף שחיק ומעבר הוגן. שמור את הבור הראשון, העוגנים הישנים, העץ הקורס הישן וכל יתר הפעולות שאושרו, אלא אם הוכח שינוי הכרחי ומוגבל והוצגה ראיית רגרסיה מלאה. אין להוסיף 'קרקע בלתי נראית' שעוקפת מכשול, ואין להסתפק ברצף שהשחקן יכול לדלג על כולו בלי לפגוש אתגרים — יש להצדיק את מיקום האתגרים במסלול הראשי.

## משימה C — העכביש בלוח Stage Modules

בדוק אם אפשר לעטוף את ה־Ceiling Spider הקיים בממשק הפעלה/כיבוי בטוח, בלי שכפול האויב. הוסף פריט אמיתי למודולים רק כאשר ON/OFF משפיע על הסצנה, מראה, התנגשות/פגיעות, AI/timers ו־restart. אם השליטה מחייבת refactor מסוכן בקוד ההיסטורי, אל תציג כפתור פיקטיבי: בצע adapter נקודתי בטוח או דווח BLOCKED מנומק עם תכנון למיילסטון נפרד. הימנע משינוי התנהגות אויב מעבר לנדרש.

## משימה D — חוזה Challenge לבונה השלבים בעתיד

הגדר מסמך וחוזה קל משקל, גרסאי, שכולל `challengeId`, גרסת schema, `requiredSkills`, `learningRole` (teach/practice/combine/mastery), `difficulty`, רשימת prefab instances וקישורים, כניסה/יציאה, חלופות פתרון, recovery, warning timing, dynamic-state assumptions ו־QA evidence. אין לפתח עכשיו generator אוטומטי או להטמיע את Platformer Challenge Forge בתוך מנוע Phaser.

בדוק מה באמת מותקן ב־Platformer Challenge Forge: לפי `FORGE_COMPATIBILITY_REPORT.md` מהחבילה, הסקיל שהותקן קודם היה M2/0.1.0 עם profile לא מאומת; אין להסתמך על תכונות M3 ללא אימות חדש. שמור את Forge **עצמאי**, ותכנן בעתיד adapter חד־כיווני: proposal → Stage JSON draft → validators → Phaser browser QA.

## משימה E — QA, הוכחת משחקיות ושחרור

1. `npm test`, `npm run build`, `npm run qa:release` או התחליף המדויק אחרי עדכון ה־release gate, תוך אימות חתימות ורישום hashes. אל תעקוף את השער באמצעות מחיקת בדיקות או הזרקת PASS.
2. בדיקות State machine: warning→collapse→aftermath→reset, שניות שונות לכל מופע, שני מופעים בו־זמנית, ביטול/כיבוי בזמן אזהרה, מוות, restart, מעבר דמות, ומניעת דליפות אובייקטים.
3. בדיקות **Chromium Phaser אמיתי** עם רצף מקשים רציף: גישה לשטח, דריכה על הגזע הראשון, זיהוי אזהרה, קפיצה ונחיתה, מעבר האתגר השני ונתיב חלופי/חילוץ בסרט. אין להציב את הדמות אחרי המכשול או לקרוא לפונקציית 'finish' ישירות כדי לדווח על חצייה. אפשר לקבוע נקודת התחלה חוקית רגע לפני רצף האתגרים, ולסמן זאת במדויק כדגימה חלקית של השלב.
4. שני השחקנים, ההבדלים ב־hitboxes, Manual/Classic/Hybrid, קלטים E/Tab/Space/חצים, והגדרות מצלמה/שער. ודא שקיימת לפחות דרך אחת מאומתת בכל תצורת דמות רלוונטית; אל תטען שכל רצף מקשים או כל קושי עביר.
5. בדוק גם **כישלון מכוון**: המתנה על גזע מתפורר גורמת לקריסה אמיתית; קריסת משטח מסירה גוף התנגשות; דרך ההתאוששות/Respawn פועלת. בנוסף בדיקות השליליות של ה־Rope Safety Validator (עוגן לא תקין נחסם לפני build).
6. שמור על baseline M472 והשווה regressions: העכביש, השורש הרקוב, העץ הנופל, דלת הסיום, הלוח המודולרי, כל האפקטים, שתי התהומות, הקלטים וסרט המדידה. אין לדרוס נכסי user או מסמכי עבר.
7. צלם ראיות התחלה/אזהרה/קריסה/חילוץ/סיום, ספק JSON מסלול ו־map לפני/אחרי, ודרג תוצאה `PASS / WARN / FAIL / NOT TESTED` עם הבדל בין source inspection, runtime simulation, Chromium, וחוויית אדם/Safari.
